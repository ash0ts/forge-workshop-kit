# Present the workshop decks

Use the deck to explain the next code change, then leave its exercise instructions on screen while participants work in the notebook. Start with the request or data, follow one intermediate value through the code, and only then open the corresponding Forge record. The [teaching sequence](teaching-sequence.md) explains this pattern and the shared diagram conventions.

Browser decks reveal one operation at a time. PDFs preserve meaningful reveal states. Worked answers live after the main sequence and link back to their exercise. Give participants time to try, but let them open an answer earlier if they need it. Identify recorded results before showing them; a participant’s unexecuted edit did not produce the capture.

Use the [workshop runbook index](README.md#workshop-runbooks-and-evidence) for schedules, and each deck’s generated presenter notes for slide-specific questions. The [deck source guide](../decks/README.md) covers local presentation; [maintenance](maintenance.md#build-the-decks) covers builds and publication.

## Pending, Inc.

Follow a billing request through the tool arguments, returned invoice, next model request, and account state. The setup trace only checks the environment; use an account-operation trace to inspect the employee’s work. Before editing a skill, check whether `read_skill` occurred. Saving the file makes it available, but does not establish that it was read.

Keep four checks distinct: `check_work` is a tool the agent can call; the participant writes a development scorer; the final grader checks fresh cases independently; the explanation judge assesses the reply. Valid judge JSON establishes that the response can be read, not that its judgment is right.

Show the deterministic retry repair separately from the later harness comparison. All three harnesses passed four final tickets in the recorded rehearsal. Extra checking changed behavior without improving those already-passing scores. [Runbook](pending-facilitator.md) · [Presenter notes](../decks/pending/notes/facilitator-notes.md).

## Solar Autoresearch

Keep one timestamp visible while showing the 60 observed samples and separate target 30 minutes ahead. Standardized inputs use training-only statistics; the target and persistence forecast remain in log-flux units. A free forward-pass check tests tensor shapes without training weights.

For images, compare prediction, target, mask, and error at the same timestamp and scale. Calculate the masked error for one image before averaging cases. Separate a settings search, a comparison of implemented architectures, and an agent-written code change. The research agent stays fixed while the forecasting models train.

Keep the unsuccessful GOES rehearsal distinct from its later teaching retest. The image recipe improved two qualification seeds and regressed on the third. [Runbook](facilitator.md) · [Qualification](solar-qualification.md) · [Presenter notes](../decks/solar/notes/facilitator-notes.md).

## Customer request routing

Follow one message through features, fitting, prediction, and review. Compute one intent’s F1 before averaging across 77 intents. Separate routing confidence from margin-based review selection and the small prompted demonstration from the full classifier evaluation. In the capstone, distinguish an incorrect label mapping from a classifier mistake. [Workshop guide](routing-workshop.md) · [Presenter notes](../decks/routing/notes/presenter.md).

## Circuit-board inspection

Keep the same board visible through whole-image features, patch distances, classifier scores, and the frozen threshold. Supplied masks help inspect defects; they are not classifier inputs. Show a corrected miss and a new miss. Active and random review receive equal labeling budgets. ## Transit software factory

Follow an after-midnight departure from service-day time to civil time, then follow a worker’s edit through testing and integration. Explain ownership with the free task-claim race. Before discussing memory benefit, show the accepted lesson, the request that actually received it, and the resulting application checks. The recorded follow-ups did not establish a benefit. [Runbook](transit-facilitator.md) · [Presenter notes](../decks/transit/notes/presenter.md).

## Airline monitoring

Show the requested change beside the flights that must remain. A successful itinerary update can still produce a wrong booking. Review outcomes before writing tag criteria, and distinguish recovered errors, unresolved requests, and appropriate refusals. Unprocessed turns are not negative judgments. The live comparison and controlled repair drill are separate examples. [Runbook](airline_monitoring-runbook.md) · [Native-feature limitations](airline-monitoring-qualification.md) · [Presenter notes](../decks/airline_monitoring/notes/presenter.md).

## Product screens and ARIA

Give each Forge screen one question: find the tool’s returned payments in Agent Lens, compare learning rates in a Sweep, open saved weights in Artifacts, or inspect matching outputs in EvalTables. Use the participant’s record where available and a labeled recording otherwise. [Evaluation publication and recovery](evaluations.md) describes the working native comparison path.

Each workshop reserves eight minutes for a development ARIA investigation and seven before Report publication. Ask for the participant’s explanation first, then examine a response and check one citation. The [ARIA guide](aria-investigations.md) covers native context, recordings, and billing. A capture establishes what ARIA said; the source record determines whether its claim is supported.
