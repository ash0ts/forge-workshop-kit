# Organize a workshop around one worked example

Open with a development example participants can inspect without credentials. Name the request, the available data, what a correct outcome would contain, and why that outcome matters. A saved execution must say that it is recorded. Reserved evaluation examples stay outside the opening and all improvement exercises.

Then connect the participant's project and use the same kind of operation for the first trace. Keep the access check short. The first investigation should concern the domain task, such as returned payments, a forecast input, or an itinerary, as soon as that operation is available.

## Order an exercise

1. Inspect an input and predict the expected behavior.
2. Explain the relevant calculation or operation beside its code.
3. Edit a bounded function and check it locally.
4. Run explicitly and inspect the output.
5. Explain whether the observation supports the prediction.
6. Follow the saved record into Forge and find the field that supports that explanation.

Keep the input, code, output, and evidence links together. Each screen has one primary next action. Browsing ahead is allowed; an unavailable execution names its prerequisite. Transport details and raw receipts can be expanded when needed.

Predictions can be spoken, discussed, or saved in an existing note. They do not need another mandatory form, and they must not silently change a measured agent's prompt. Show worked answers after the diagnostic prompt, with an explicit option to open them earlier.

## Introduce automation after its decisions

Run one configuration before a Sweep, one request before a batch, and one builder before a team. Inspect a baseline's validation errors before implementing an alternative representation. Review domain outcomes before writing a judge rubric or monitoring criterion.

Before asking an editor to select or compose candidates, have participants read the diffs, compare probes, and suggest which version to keep. The agent's decision then provides something they can compare with their own reasoning. Keep retained versions, unsuccessful changes, and missing judgments visible.

## Keep slides and controls aligned

Follow the same case and intermediate values in both surfaces. A reveal answers a question raised on the preceding state. Put the relevant code beside the transformation and label simplified arithmetic. Explain the mechanism before opening its product capture. Presenter notes add likely misunderstandings and timing; the slide itself remains understandable.

Use Agent Lens to locate an operation, runs and Sweeps to compare experiments, Artifacts to reproduce saved files, and EvalTables to inspect matching cases. Native tag criteria and Alignment answer whether a monitor agrees with reviewed examples. Each product link gets one specific investigation task.

## Use consistent visual conventions

Use the [technical-manual skill and figure sources](technical-visuals.md) for the shared diagrams and posters. Their templates define the type, spacing, lines, and reveal geometry. Keep real photographs, scientific scales, and native captures in their original colors.

Keep the same case and values in stable positions across reveals. Label inputs, outputs, units, and tensor shapes beside the corresponding code. A screenshot annotation should point to an actual field without hiding its value; retain the original capture and its source link. Next/Back and case selectors only change what is displayed, never execute the experiment.

For candidate branches, use gray for the parent, blue for Candidate A, and orange for Candidate B. Composition uses a neutral decision card. Solid arrows show code or execution flow; dashed arrows show reviewed evidence. Color never indicates quality. Label the selection and status in text.

Selecting a saved branch should show its intent, actual diff, probe result, decision, and Forge links. **Retain this version** means unchanged code, with the reason. Proposed or planned work has no execution or trace until one is recorded. Do not draw an invented improvement conversation for a manual edit.

The [deck guide](deck-guide.md) describes the objects and distinctions to follow in each workshop. The domain runbooks own the data rules and calculations; publication recovery stays in [evaluations](evaluations.md).

## Ask ARIA after the participant has an interpretation

Schedule an eight-minute development investigation before the proposed intervention and a seven-minute conclusion check before Report publication. Reuse discussion time. Show the selected case and versions, the participant’s hypothesis, an actual ARIA response, and the source used to check one claim. The question, response, and verification remain separate frames in the deck and explicit actions in the notebook.

Use the [ARIA investigation contract](aria-investigations.md). Early context contains only allowed development or validation records. Closing suggestions concern a future experiment. No answer automatically becomes a prompt, label, rubric, lesson, or release decision. Personal-project participants use the recorded exercise; unavailable recordings remain unavailable.

## Teaching references

The sequence adapts the small Python implementations and recurring evaluation in [Andrew Ng's agentic-AI course](https://www.deeplearning.ai/courses/agentic-ai), domain review and judge calibration in [Hamel Husain's evaluation guidance](https://hamel.dev/blog/posts/evals/), and early working applications in [fast.ai's teaching approach](https://www.fast.ai/posts/2016-10-08-overview.html). These are references, not endorsements or reviews of this kit.

Keep the office, research lab, support queue, factory inspection, transit team, and airline settings specific. Humor belongs in their situations. Buttons and execution instructions should say exactly what will happen.
